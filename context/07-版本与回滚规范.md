# 07-版本与回滚规范

> 2026-08-04 用户定稿：**git 基线铁律**——AI 写的代码人工不敢维护不敢动，解法 = git 兜底 + 每次只让 AI 改一小块 + 架构地图（用户管边界/哪些能动，AI 管代码）。

## 1. git 基线铁律

1. **关键版本必 commit + tag**：好版本打 tag（如 `v54-best`、`v114-final`），改坏秒回
2. **每次只让 AI 改一小块**：单文件修改优先，多文件大改要拆解
3. **架构地图**：用户管「哪些能动哪些不能动」（见 context/04 边界），AI 管代码
4. **教训**：跟嘴最好的 v54 曾回不去 = 无 git 基线；v100 时代全靠 versions/ 快照 + 记忆，太脆弱

## 2. 版本快照机制（versions/ 目录）

```
每轮修改后：
1. 把本轮改动文件复制到 versions/v{n}/（n 递增）
2. 写 versions/v{n}/README.md（改动摘要）
3. 更新 AGENTS.md「当前状态」版本号与摘要表
4. 旧版本文件不删除，保留完整历史
5. 汇报时给出当前版本号 v{n} + 改动文件清单
```

回滚 = 把 versions/v{n-1}/ 文件复制回源码位置。

## 3. 与 git 的双轨

| 层 | 机制 | 用途 |
|---|---|---|
| versions/ 快照 | 仓库内目录 | AI 每轮改动的细粒度记录 |
| git commit + tag | 版本基线 | 关键节点、可回滚点 |

- versions/ 是**过程记录**（每轮都留）
- git tag 是**里程碑**（好版本才打，如 v54-best / v114-final）
- 两者不冲突：versions/ 保证细粒度，git 保证秒回

## 4. git 操作规范

```
- 不 commit/push/部署：除非用户明确要求（AI 红线）
- commit 备注：仔细写清变更内容，不一把梭（git log 是项目最权威变更时间线）
- 检查项目第一步：git log → git diff → 才扫文件目录
- push 前：逐仓库 git status 核实改动只落对项目
- 并行 AI 任务：只改不 commit，最后统一由用户确认后 push
```

## 5. 回滚流程

```bash
# 场景：改坏了，回到上个里程碑
git tag                              # 查看所有 tag
git checkout v114-final -- src/      # 只回退 src/（保留其他）
# 或整体回退
git checkout v114-final
```

```bash
# 场景：versions/ 快照回滚（无 git tag 时）
cp versions/v113/src/hooks/useStreamingAsr.ts src/hooks/useStreamingAsr.ts
```

## 7. 打包交付规范

```
- 对外汇报前（同一轮内）：npm run build → 更新根目录 jarvis-voice.zip
- 命令：rm -f jarvis-voice.zip && cd dist && zip -rq ../jarvis-voice.zip .
- 汇报必须写明 zip mtime + 主 bundle 文件名（index-*.js）
- 前后端都改时：发两个包（jarvis-voice.zip + jarvis-asr-stream.zip）
```
